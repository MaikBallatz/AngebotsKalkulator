# Design System

> The LOOK. Read this before touching anything under `app/views/`.
> `requirements.md` is the WHAT, `CLAUDE.md` is the HOW — this file is the third leg: how it looks.

**The values live in exactly one place: `app/assets/tailwind/application.css`, in the `@theme` block.**
This file never repeats a hex value — it explains what each token *means* and which components use it.
One source, no drift.

To apply a customer's corporate design, run **`/design-system <url, description, or file>`**.

**To see it: `http://localhost:3000/design`.** Every component below, rendered with the current
tokens, each token labelled with its name. That page is generated by `/init-project` and needs no
maintenance — it reads the same tokens as the rest of the app, so it can never drift from reality.
Send anyone there who asks what the app will look like, or who wants to change something and lacks
the word for it.

---

## The rule that makes this work

**Never write a raw color, radius or font into a view.** No `bg-blue-600`, no `bg-[#E2001A]`,
no inline styles. If something is missing, it becomes a token first — then you use it.

That single rule is why the tenth feature looks like the first, and why swapping a corporate
design takes one edit instead of an afternoon.

---

## Token roles

Tailwind v4 turns every token in `@theme` into utilities automatically: `--color-brand-600`
gives you `bg-brand-600`, `text-brand-600`, `border-brand-600`; `--radius-card` gives you `rounded-card`.

| Token | Role |
|---|---|
| `--color-brand-50` | very light tint of the accent — subtle backgrounds, highlights |
| `--color-brand-600` | the accent: primary buttons, links, focus rings |
| `--color-brand-700` | accent hover — same hue, ~10% darker |
| `--color-brand-ink` | text placed **on** the accent; must reach 4.5:1 contrast against `brand-600` |
| `--color-page` | app background |
| `--color-surface` | cards, nav bar, panels |
| `--color-muted` | active nav item, selected or hovered rows |
| `--color-ink` | headings and primary text |
| `--color-ink-soft` | labels, secondary text |
| `--color-ink-muted` | hints, captions, table headers |
| `--color-line` | structural lines: dividers, table borders |
| `--color-line-strong` | control borders: inputs, secondary buttons |
| `--radius-card` | cards and panels |
| `--radius-control` | buttons, inputs, flash messages |
| `--font-sans` | the app's type stack |

**Status colors stay Tailwind defaults** (`red-*` for errors, `green-*` for confirmations).
Red means error in every product — that is a convention, not a brand decision. Turn them into
tokens only if the brand explicitly defines its own error and success colors.

| Step tracker | compact multi-step progress, `flex items-center mb-6`; each step a circle `h-8 w-8 rounded-full flex items-center justify-center text-xs font-medium flex-shrink-0`, joined by a connector `flex-1 h-px bg-line mx-1`. Jeder Kreis braucht ein `aria-label` der Form `"<Name> — erledigt\|aktuell\|offen"`, weil ein Häkchen ohne Text am Screenreader nichts sagt. **Nur wenn die Namen der Stationen selbst die Botschaft sind** — sonst der schlichte Step tracker, vier beschriftete Spalten kosten viel Breite |
| Nachschlage-Kachel | eine Card in klein, bei der **die ganze Kachel der Link ist**: `block bg-surface rounded-card shadow p-4 hover:bg-muted`, darin ein Section heading und genau eine Zeile Muted text. **Kein Button darin** — zwei Klickziele in einer Kachel sind eins zu viel, und ein Button neben einem klickbaren Hintergrund lässt offen, was von beidem gilt. Für Verweise auf Seiten, die man nachschlägt, nicht für Aktionen; mehrere davon in einem `grid grid-cols-2 md:grid-cols-4 gap-4` |
| Startschritt | eine nummerierte Aktionszeile in einer Card; mehrere davon untereinander, getrennt durch `border-t border-line`. Zeile `flex items-start gap-4 py-4`: links der Kreis aus **Step tracker** — dieselben drei Zustände, dieselben Klassen, aus `step_circle_classes` — rechts ein Section heading, rechtsbündig daneben optional ein Muted text als Standanzeige („Schritt 3 von 9"), darunter eine Zeile Muted text und **genau eine** primäre Aktion. Für einen kurzen festen Weg von zwei, drei Schritten, den man auf einen Blick lesen soll. **Nicht** als Ersatz für den Step tracker: der zeigt viele Schritte kompakt, dieser zeigt wenige Schritte mit ihrer Aktion |
| Folien-Ansicht | `<iframe>` mit `w-full h-[80vh] rounded-card border border-line`, dazu ein Link „in eigenem Tab öffnen" für volle Breite und Tastaturnavigation. **Folien als HTML einbetten, nie als PDF verlinken** — bei einer PDF entscheidet die Browser-Einstellung, ob sie angezeigt oder heruntergeladen wird, und im Workshop laufen fremde Rechner. Ein Browser ohne PDF-Betrachter zeigt einen leeren Rahmen, ohne Fehlermeldung. HTML zeigt jeder |
| Empty state | centered, `text-ink-muted`, call-to-action button — see the icon rule below |

**If a screen needs a pattern that isn't in this table:** add it here first, then use it.
Never leave a one-off style in a view — that is how a design system erodes in an afternoon.

**Deliberately not in this table:** modals, tabs, pagination, dropdown menus, avatars,
breadcrumbs, loading states. None of them survive the cut in a two-day build, and every extra
row is one more thing to pick wrongly. If a screen truly needs one, the rule above applies.

### Every screen

Three questions a screen answers without anyone having to think. They are checkable,
which is the only reason they are here rather than in a principle nobody applies:

1. **Where am I?** A heading that names this screen in the words of the domain — not
   "Index", not "Übersicht". The nav shows the app; the heading shows the place.
2. **What can I do here?** The most likely next action is a **button**, in view, not a
   menu entry the user has to find. One screen, one obvious action.
3. **What happens next?** After every save, delete or submit: a flash message that says
   what happened, and a screen that shows the result — never a form that simply empties.

And one prohibition that carries all three: **no abbreviation, no jargon, no field
without a label.** The people using these apps are experts in their work and strangers
to this software. Every word they have to decode is a word we chose badly.

### Destructive actions

**No modal component.** Rails already ships the confirmation, and it needs no JavaScript of ours:

```erb
<%= button_to "Löschen", interview_path(@interview), method: :delete,
      form: { data: { turbo_confirm: "Wirklich löschen? Das lässt sich nicht rückgängig machen." } },
      class: "bg-red-600 hover:bg-red-700 text-white font-medium py-2 px-4 rounded-control" %>
```

Every destructive action gets one. The dialog is the browser's, so it looks plain — that is the
correct trade for a two-day build, and a plain dialog nobody has to build beats a pretty one
that swallows a click on the wrong laptop.

### Loading

Turbo already draws a progress bar on every navigation. It is blue by default; `application.css`
restyles it to `--color-brand-600` below the `@theme` block, so it follows the brand along with
everything else. **Do not build spinners.** If an action is slow enough to need one, it belongs
in a background job — which is out of scope here.

### Icons

**No icon library.** Not a webfont, not a CDN, not a gem. A hackathon app runs on a laptop that
may be on hotel wifi, and a missing icon set is an invisible break that costs an afternoon.

When a screen genuinely needs a symbol, write an **inline SVG with `fill="currentColor"` or
`stroke="currentColor"`** and size it with `h-5 w-5`. It then inherits the surrounding text
colour and follows the brand automatically — no token, no maintenance.

Emoji are acceptable in an empty state and nowhere else. They render differently on every
machine, which is fine for one decorative glyph and wrong for anything a user has to read.

Layout conventions: page container `max-w-7xl mx-auto px-4 sm:px-6 lg:px-8`, vertical
section rhythm `py-8`, card padding `p-6`, control padding `py-2 px-4`.
